# Minecraft Agent 设计（干净版）

> 这份文档是**目标形态**，不是现状快照。写它的目的是给仓库里每一行代码一个判据：
> 符合它的留，冲突的改，剩下的删。
> 范本：Pi（`github.com/earendil-works/pi`，`packages/coding-agent`）、OpenCode、DSH。
> 状态：2026-10-06，上下文机制与请求日志已按本文实现（见 §4、§5 的"已实现"标记）。

---

## 0. 一句话

**它就是一个普通的 agent，和 Pi / OpenCode / DSH 没有本质区别。**

ReAct 循环 + 一组工具 + 一份上下文。唯一的区别是：

1. **工具不是终端读写，而是《我的世界》里的操作**（走过去、挖方块、合成、攻击……）；
2. **上下文末尾多注入一段 Live State**（每轮现采的世界快照）。

除此之外，循环怎么转、事件怎么排队、上下文怎么压、日志怎么写、工具怎么校验——
都应该和那些 agent 一模一样。**不能把它和那些 agent 割裂开来设计。**

## 1. 骨架

```
mineflayer bot（20 tps）
   │  世界事件 / 玩家聊天
   ▼
Scheduler ── 决定"这个事件要不要唤醒模型、要不要打断在途回合"
   │
   ▼
AgentLoop ── 一轮 = 组上下文 → 问模型 → 顺序跑它的工具调用 → 回填 → 直到 Finish
   │
   ├── History   ── 完整对话 + 压仓（Pi 式）
   ├── Tools     ── 52 个类型化工具（47 MC 操作 + 5 控制类）
   └── LiveState ── 每轮现采，拼在这次请求的最后
```

**一次 API 请求的完整形态**（没有别的了）：

```
[system]     系统提示词（固定前缀，吃 prompt cache）
[user]       …完整历史里的第 1 条…
[assistant]  …完整历史里的第 2 条…
   ⋮
[user]       ## 事件（本轮 unseen） + ## 当前世界快照   ← 这一轮的尾巴，永远在最后
```

`tool_choice: required`：每轮至少调一个工具（想说话调 `Say`，收工调 `Finish`），
空响应永远卡不住循环。

## 2. 与通用 agent 的逐项映射

设计时不要发明新概念，先把通用 agent 的零件对上号：

| 通用 agent（Pi / OpenCode / DSH） | 本 agent |
|---|---|
| `read` / `write` / `edit` / `bash` / `grep` | `goToPlayer` / `collectBlocks` / `craftRecipe` / `attack` / `searchForBlock`… |
| 用户消息 | 玩家聊天 / 私聊 / 任务目标 |
| 环境提示（cwd、git 状态、打开的文件） | **Live State**（血量、背包、坐标、附近实体/方块、计划） |
| `ESC` / 双击 ESC 打断当前回答 | **L4 抢占** |
| 会话压缩（`/compact`、自动 compact） | **压仓**（§4） |
| 工具审批 / 权限模式 | `blocked_actions` + profile |
| 后台任务完成通知 | 动作完成 → L3 Tool 事件（§3） |
| 会话文件 / transcript | `memory.json`（turns）+ `histories/*.json`（归档）+ `logs/request-00N.log` |

## 3. 事件分级 = 标准 agent 原语

分级不是"游戏特供"，它就是 agent 里本来就有的几种"打断强度"：

| 级 | 语义 | 通用 agent 里的对应物 | 动作线 |
|---|---|---|---|
| **L1** | 只记账，永不唤醒 | 遥测 / 统计 | 不动 |
| **L2** | 记账，随下一次请求顺带带上 | 环境噪声、状态更新 | 不动 |
| **L3** | **放进消息队列**：推理线空闲就立刻起一轮，忙就排到本轮结束 | 后台任务完成通知、队友消息 | 不动 |
| **L4** | **打断当前回答**，事件由重启的那一轮带上 | 按 ESC 停掉当前回答 | **不动，继续跑** |
| **L5** | **冻住整个 agent**：停推理 + 停动作 + 锁死动作通道；跑完保命脚本再解冻 | 急停 / Ctrl-C | 停 |

要点：

- **L3 是常态**。心跳、挨打、拾取、玩家靠近，全都走 L3：写进历史，下一轮带上。
  一次唤醒就是一次完整的模型请求，所以 L3 的判定标准只有一个：
  **"这件事值不值得让模型看一眼"**。当前 `edges.ts` 的滞留/抖动门限就是干这个的。
- **L4 不是"停动作"**。它等价于"把当前回答掐掉重开"，身体上的活儿该继续继续。
  这条以前被写反过（模型一被打断就去 `Stop`），见 §6。
- **L5 是唯一的硬中断**：它绕过模型（`emergency.ts` 全程不调模型），
  只经 `EmergencyBot` 做保命动作，结束后 `endEmergency()` 决定要不要接着唤醒。

### 3.1 事件系统 = 消息队列 + 打断（不是新物种）

**这套事件系统没有改造消息队列，它用的就是消息队列的原生机制**：
把事件塞进队列，然后在特定时候"打断一下"这个队列。用主流 agent 的术语说，
DSH 里的两个概念正好对上：

| DSH 术语 | 含义 | 本文的事件级 |
|---|---|---|
| **引导（steer）** | 提示词在 agent 干活期间发过去，**下一次 API 请求带上** | **L3（推理线忙 → queued）**、**L4（打断当前回答后重开）** |
| **排队（queue）** | 等 agent **完全结束工作**（Finish 完）之后再把提示词发过去，把它重新拉起来 | **L3（推理线空闲 → start）**，以及 `finishRequest` 发现还有未见的 L3+ 事件时再起一轮 |

逐条对上：

| 事件级 | 队列动作 | 与通用 agent 的等价物 |
|---|---|---|
| L1 | 入队，**永不进上下文**（`beginRequest` 只收 level ≥ 2） | 遥测台账 |
| L2 | 入队，不唤醒，随下一次请求顺带 | 环境噪声 |
| L3（空闲） | 入队 → 立刻起一轮 | **排队**：干完这一段继续干 |
| L3（忙） | 入队 → 本轮结束后带上 | **引导**：下一次 API 请求带上 |
| L4 | 打断在途请求 → 事件交给重启的那一轮 | **引导 + 打断**（等价按 ESC） |
| L5 | 冻结：停推理、停动作、锁通道 → 保命 → 解冻 | 急停 |

所以"事件系统看起来和主流 agent 不一样"只是外观：**内核就是队列 + 打断**，
和 steer / queue 是一回事。这条也是迁移改动量小的根本原因。

### 3.2 为什么迁到 Pi 这类框架

迁移的动机（针对 pi-durable Work Tree 那条路径，但设计思想对本文同样成立）：

1. **一切皆插件**：将来往上挂工具是纯增量，不用改主循环。
2. **框架自带恢复、上下文压缩、上下文管理**：正是本项目 §4 手写的那一整套
   （触发线、切点、摘要、溢出恢复），迁过去直接用，不重复造轮子。
3. **我们要写的只剩两件事**：**把工具写出来** + **注入一个 Live State**。
4. 事件系统无需重新设计：原生消息队列 + 打断，就是 §3.1。

> 本文 §4 / §5 应当被读作**规格**而不是"某一份实现"：
> 在 `mindcraft-ce` 里由 `compaction.ts` / `history.ts` 原生实现；
> 在 pi-durable 路径里由框架的 `CompactionTask` / `Conversation` 提供。
> 两条路径必须满足同一组可观测语义（何时压、压掉什么、摘要长什么样、日志怎么翻页），
> 否则两个分支会漂。

## 4. 上下文规则（照 Pi，已实现）

**第一原则：发给模型的是完整上下文。** 没有"最近 N 条"、没有"历史尾巴 token 预算"。
唯一的裁剪机制是压仓。`max_messages` 这种东西不该存在——窗口还很空的时候按条数压仓，
只是把可用上下文换成一段有损摘要，模型就会看不到自己干过什么。

1. **触发线**：`contextTokens > contextWindow - reserveTokens`
   - `contextTokens` 优先取**上一条 assistant 回复里 provider 报的 `usage`**；
     只有它之后新增的条目才用估算补（CJK≈1 token/字，ASCII≈1/4，故意往大估）。
   - 锚点不能跨越压仓边界：压仓前产生的 usage 已经过期，不能再当基线。
   - 默认 `reserveTokens = 16384`（给回复留位置）。
   - 窗口来自 profile：`context_window`。`deepseek-v4.1-flash` @ OpenCode Go = **1000000**。
2. **切点**：从最新往前累加，攒够 `keepRecentTokens`（默认 20000）就切；
   只在 user/assistant 边界切，**绝不切在工具回执上**；该位置没有合法切点时退到最后一个合法切点。
3. **压仓 = 追加一条摘要条目**，不删历史。摘要覆盖头部，尾部逐字保留。
   模型看到的变成：`system + 结构化摘要 + 保留段`。
4. **摘要格式是结构化的**（照 Pi）：
   `## 目标 / ## 约束与偏好 / ## 进展（已完成·进行中·受阻）/ ## 关键决定 / ## 下一步 / ## 关键上下文`。
   头部第一条是上一轮摘要时走**更新版**指令（`<previous-summary>` 迭代，不是重新摘要）。
   交给摘要模型的是 `[User]: / [Assistant]: / [Tool result]:` 台账（单条截断 2000 字），
   不是原样多轮消息——否则它会接着最后一条 assistant 继续写。
5. **溢出恢复**：provider 报 `context_length_exceeded` 或 `finish_reason: length` 时，
   强制压一次并**重试一次**；再失败才认输。

> 实现：`src/agent/compaction.ts`（策略，纯函数）、`src/agent/history.ts`（驱动 + 落盘）、
> `src/models/gpt.ts`（`usage` / `overflow`）、`src/utils/text.ts`（`toLlmMessages` / `serializeConversation`）。

### 4.1 两条不可颠倒的原则

这两条是"为什么不能拿现成 agent + MCP 凑出来"的答案，也是本项目的边界：

1. **Live State 每轮现采、注入在请求末尾，并且不进历史。**
   它不是一条消息，是一层"感知"：模型这轮看到的血量/背包/坐标，下一轮必须重新采。
   一旦它进了历史，就会变成一个"当时看到的"陈旧快照躺在上下文里，既浪费窗口又误导模型。
   MCP 做不到这件事——工具调用的结果必然留在上下文里；不提供工具，模型就完全瞎。

   > 代码事实：`assembleContext()` 拼出的尾巴只作为**最后一条 user 消息**发出
   > （`gpt.sendRequestWithTools` 的 `liveTail`），**从不写进 `history.turns`**。

2. **每个事件进上下文恰好一次。**
   队列里的东西（玩家说话、世界事件、动作回报）要么在历史里，要么在尾巴里，
   不能两边都出现，也不能两边都没有。

   > **已收口（2026-10-06）**：事件台账是唯一入口——`AgentLoop.notify()` 拿到调度器分配的
   > `seq` 后调 `onEvent` → `History.addEvent()`，玩家消息落成自然的 user 轮次
   > （`#15 bobo: …`），世界事件落成一条带序号的 system 行（`#16 World/L3 {…}`）。
   > 尾巴里的 `## 事件` 只剩唤醒标记：`## 本轮新事件` + `#15 #16`，**正文不再重发**。
   > 修掉了两个方向的老问题：玩家消息在同一请求里被喂两遍；世界事件（挨打、拾取、缺氧）
   > 只活在尾巴里、从不进历史，这轮不渲染就彻底消失。
   >
   > 事件入账是同步的（在调度器回调里，不能 await 压缩），所以压仓的检查点放在
   > **每次请求之前**（`modelCall`）——那也正是 Pi 的位置。

### 4.2 `stats`：Live State 的"可留存版本"

两者**同源**（`Agent.liveStateText()` 一份采样），区别只在谁把它写进台账：

| | Live State（尾巴） | `stats` 工具（历史） |
|---|---|---|
| 何时产生 | 每轮请求前自动现采 | 模型主动调用 |
| 是否入历史 | **否**（感知层，下一轮重新采） | **是**（Tool 回执，永久留存） |
| 用途 | "我现在是什么样" | "**我上次看的时候**是什么样" —— 可对比 |

所以 `stats` 不是"查状态的备用手段"，而是一张模型自己决定何时拍的照片：
它可以拿两次快照比较"这期间我多了什么、走到哪了"。VLM-Bot 当初想用 Live State
彻底取代查询类工具，那是激进的做法；留一个可留存的快照是有价值的。

## 5. 请求日志（已实现）

**一个文件 = 一代上下文。**

```
bots/<name>/logs/request-001.log   ← 每次请求覆盖写，永远是最新一次
                                   ← 压仓发生时序号 +1，之后写 request-002.log
```

文件内容 = 这次请求真正发出去的东西（system 正文 + 每一条消息 + 末尾尾巴，
有截图就标一条）。头三行是 `# request at` / `# round` / `# tools`。

不追加、不 JSONL：追加式日志要回答"上一轮模型看到了什么"必须往回翻，
而且压缩点和文件边界对不上，复盘时分不清某条历史是压前还是压后。

> 实现：`src/agent/requestLog.ts`；写盘在 `src/models/prompter.ts::logRequest`；
> 翻页钩子在 `src/agent/history.ts::runCompaction`。

## 6. 工具契约

- **类型化 + 校验**：每个工具带 JSON Schema，调用前 `validateToolCall` 把
  未知工具/未知参数/缺必填/类型错/越界都变成带路径的 verdict，而不是抛错。
- **两类工具，两种时间观**：
  - 查询类（只读）：阻塞执行，直接回内容；
  - 动作类（占身体）：认领通道 → 后台跑 → 立刻回 `accepted`，跑完以 Tool 事件回到 L3。
- **控制类**（`Finish` / `Stop` / `Say` / `UpdatePlan` / `Feedback`）：不占身体通道。
- **同一时刻最多一个占用型动作**；动作类串行是底线。

**身体通道只有一套**（2026-10-06 合并完成）：

- `Scheduler.action` 是**唯一真相**：`action_runner.ts` 认领/释放，同一时刻最多一个动作。
- `ActionManager` 退化成**薄执行器**：跑动作函数、维护 `executing`、收集输出摘要、超时中断。
  它不再有自己的"忙/闲"判据去打断别人。
- **resume 机制整体删除**：它被 `followPlayer` 用过一次（`runAsAction(fn, true)`），
  做的是"每次 bot idle 就把上一个动作偷偷重放一遍"——一个绕过通道、模型不知情的
  隐藏决策者，导致"跟随"永远停不下来。现在 `followPlayer` 就是一个正常的占用型动作：
  **一直占着身体通道，直到模型调 `Stop`**。
- 因此两条契约缺陷都已修掉：
  1. **忙时同动作幂等**：请求的动作就是正在跑的那个 → 回「已经在做了」，不催 `Stop`；
     确实是另一个动作 → 报清楚"谁在跑、跑了多久"，要不要打断交还模型判断。
  2. **`Stop` 一次停干净且说真话**：`stopAll()` 当场释放通道并回报
     `{had_action, stopped_action, generation}`；`ActionManager.stop()` 会**等**身体真的
     停下来才返回（10 秒兜底才杀进程）。

## 9. 不要在这里重建 Pi（决策记录，2026-10-06）

审计后确认还有 6 处"离 Pi 还差一点"，但**决定不在本仓库实现它们**：

| # | 差距 | 为什么不在这里做 |
|---|---|---|
| ① | 工具是硬编码列表，不是 `defineTool` 注册表 | 那是 Pi 的核心能力；在这里实现一遍等于重造一个 Pi |
| ② | 评测任务框架嵌在 agent 主循环（`tasks.ts`） | 属于"外壳 vs 核心"的划分，取决于最终用哪套运行时 |
| ③ | `full_state.ts`（UI）与 `live_state.ts`（模型）两套状态渲染 | 同上的外壳问题 |
| ④ | 三份持久化（memory.json / histories / logs） | Pi 的 append-only session 白送这一条 |
| ⑤ | MindServer 外壳被 agent 核心 import | 需要先定下运行时边界 |
| ⑥ | `ActionManager` 残余（`isBusy` 的第二个答案） | 收益小，风险中等 |

**理由**：另一条线（`mindcraft-ce-pi-durable` worktree）正在把本项目迁到
`@earendil-works/pi-durable`。如果那条线跑通，①②④ 就是框架自带的能力，
本仓库只需要提供**工具集 + Live State 注入**两件事。

**因此本仓库的定位是**：

1. **不依赖任何框架的备份实现** —— 万一那个框架不成熟、或将来做出对我们不利的改动，
   这里有一条能跑的独立路径（这也是双线并行的初衷）；
2. **语义规格的载体** —— §3（事件=队列+打断）、§4（上下文与压仓）、§4.1/§4.2、
   §6（工具契约）描述的是**两条线都必须满足的可观测行为**，不是某一份实现。
   迁移过去时按这套语义验收，而不是按代码逐行对照。

**什么时候回来做 ①②④**：只在那个框架被判定不可用时。否则不要在两条线上各实现一遍。

## 10. 迁移验收清单（两条线共同的可观测契约）

pi-durable 那条线跑起来后，照这份清单逐条验。**每条都给了可观测证据**——
不看代码，看日志/工具回执就能判。任一条不过，就说这条语义没迁过去。

### A. 上下文

| # | 契约 | 怎么验 |
|---|---|---|
| A1 | 历史**完整**发送，不按条数/尾巴预算截断 | 跑 30+ 轮后，早期轮次的内容仍能在请求里找到；不存在"最近 N 条"的行为 |
| A2 | 压仓触发线是**窗口压力**，不是条数 | 窗口 1M 的模型上，几百条消息也不该触发压仓 |
| A3 | 锚点是 **provider 报的真实 `usage`** | 每轮响应的 usage 被记录；压仓时刻与 `contextWindow - reserve` 吻合 |
| A4 | 切点**不切在工具回执上** | 压仓后保留段的第一条是 user/assistant，不是工具结果 |
| A5 | 压仓**只追加摘要**，不丢原文 | 压仓后仍能查到被压掉的原始条目（归档/投影）；摘要进历史头部 |
| A6 | 摘要用 Pi 的结构化格式 | 摘要含 目标/约束/进展/关键决定/下一步/关键上下文；二次压仓走"更新"语义 |
| A7 | 溢出可恢复 | 人为把窗口调小 → 触发一次压缩重试，而不是直接报错退出 |

### B. 事件（= 消息队列 + 打断）

| # | 契约 | 怎么验 |
|---|---|---|
| B1 | L3 空闲 → 立刻起一轮；忙碌 → 本轮结束后带上 | **排队 / 引导** 两种时机都能在日志里看到 |
| B2 | L4 打断在途回答并重开，**动作不受影响** | 触发 L4 后当前工具动作仍在跑（未被 Stop） |
| B3 | L5 冻结全部、跑保命、再解冻 | emergency 期间没有模型请求；结束后恢复 |
| B4 | **每个事件进上下文恰好一次** | 同一条玩家消息在同一个请求里只出现一次；世界事件（挨打/拾取）能在历史里查到 |
| B5 | 唤醒有原因 | 请求里有"本轮新事件"标记，且能在历史里按序号找到对应正文 |

### C. Live State 与快照

| # | 契约 | 怎么验 |
|---|---|---|
| C1 | Live State **每轮现采、注入末尾、不进历史** | 连续两轮请求里快照会变；历史里搜不到旧快照 |
| C2 | 快照永远在请求最后 | 最后一条 user 消息以世界快照收尾 |
| C3 | `stats` 是**同源快照且留存** | stats 回执与同轮尾巴内容一致；它作为 Tool 回执留在历史里，可跨轮比对 |

### D. 请求日志

| # | 契约 | 怎么验 |
|---|---|---|
| D1 | **一个文件 = 一代上下文**，每次请求覆盖写 | 连发两次请求，文件里只有后一次 |
| D2 | 压仓时**翻页**（`request-001` → `002`） | 压仓后新文件出现，旧文件保留 |
| D3 | 日志 = 模型实际收到的消息列 | 打开文件能看到 system / 各轮消息 / 本轮尾巴；不含内部字段（`kind/level/at/usage`） |

### E. 工具契约

| # | 契约 | 怎么验 |
|---|---|---|
| E1 | 请求的动作**就是在跑的那个** → 幂等忽略 | 回执是"已经在做了"，**不是** `Stop() first, then retry`；动作没有被中断 |
| E2 | 确实是另一个动作 → 说明谁在跑、跑多久，不命令 Stop | 回执含在跑的动作名/时长 |
| E3 | `Stop` 一次停干净 | Stop 返回后立刻能起新动作，不需要"再 Stop 一次" |
| E4 | `Stop` 说真话 | 本来没在跑时如实回报 `had_action: false` |

### F. 提示词

| # | 契约 | 怎么验 |
|---|---|---|
| F1 | 不再教模型"通道忙就先 Stop" | 提示词里没有这条指令 |
| F2 | 明确"被叫醒 ≠ 动作出错" | 提示词要求先看当前 action 再决定 |

> **注意**：清单里 B2/E1/E3 是最容易在迁移中丢掉的——它们不是框架自带的东西，
> 而是本项目踩过的坑。迁过去时这几条要专门写测试钉住。
